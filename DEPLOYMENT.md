# RescueRoute1 deployment and verification

## Required services and free-tier caveats

A MongoDB Atlas M0 free cluster is the intended database. Render's free web service can host the Express API and a free static site can host the frontend. Free-tier limits, inactivity sleep, network policies and AI quotas are provider-controlled; check the current plan before provisioning. Do not switch to a paid tier without the owner's approval.

The codebase does not include a production admin account or sample data. The original destructive demo seed script was removed; use isolated test data only. Ask the owner to provision the first admin account securely once production MongoDB exists; public `/api/auth/register` cannot create an ADMIN.

## Backend

Deploy the `backend` directory as a Node web service. Build: `npm ci`; start: `npm start`; health check: `/api/health`. Configure these Render environment variables (never commit the values):

- `NODE_ENV=production`
- `MONGODB_URI`: Atlas application-user connection URI with a dedicated database name.
- `JWT_SECRET`: a random secret of at least 32 characters, generated by the platform.
- `CLIENT_URL`: exact HTTPS origin of the deployed frontend (no trailing slash).
- `GEMINI_API_KEY`: optional server-side key; Gemini is informational only. Free quotas apply.

Do not leave `MONGODB_URI` unset or enable open network access without a conscious security review. The API does not listen if the database is unavailable. `/api/health` returns HTTP 503 while disconnected.

## Frontend

Build at project root with `npm ci && npm run build`; publish the `dist` directory with SPA rewrite `/* -> /index.html`. Set `VITE_API_URL` to the exact backend origin **plus `/api`**, e.g. `https://your-backend.onrender.com/api`. This is baked into the Vite build. When the static site URL is known, set `CLIENT_URL` on the backend to its exact HTTPS origin and redeploy if needed. A raw host without `https://` and `/api` is not a valid value.

## Validate before handoff

1. Confirm the backend health endpoint reports `database: connected` and HTTP 200.
2. Check the frontend opens without a console/network error and that registration rejects `ADMIN`.
3. Test a donor, shelter and driver account using private test identities in an **isolated test database**, then verify post -> match -> accept -> dispatch -> pickup -> delivery and public request/admin workflows. Do not use the development seed on production.
4. Confirm a missing API or database displays an error, never a simulated record; impact starts at zero on an empty database.
5. Check the map displays only stored coordinates and impact does not mix meal counts with weight or show an unverified CO2e claim.
6. Re-run `npm run build` in the root and tests with a live isolated MongoDB. Record actual results and deployment URLs; do not claim tests passed if they were skipped for a missing database.
